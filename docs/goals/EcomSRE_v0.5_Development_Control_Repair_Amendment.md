## 1. 已核对事实：先区分三类问题

- N1：实际启动并触发队列条件，但 incident 创建前发生 `HTTP 422`，原因是服务 ID 未排序。它已消耗槽位；没有可恢复的指定资源窗口。相关输入验证已经修复，不重做同一修复，不填造旧数据。
- N2：独立健康开发事件，返回 `NO_INCIDENT`；保留使用，不重新采集来增加分母。
- N3：采集完成但返回 `INSUFFICIENT_EVIDENCE`。记录有 payment 错误指标和错误 spans，但没有被当前规则认可的 first-error 因果身份。Changes 为空、Runtime 健康；原始父子 span 图没有保留。
- Trace 输出存在截断，但 first-error 身份在截断前计算，因此不能直接把截断判定为缺失标记的原因，也不能通过增大结果上限或手改标记制造已知诊断。
- 新部署 04 的资源清理与非项目状态核对通过。之前 Hermes/Resource Saver 的阻塞历史保留，但它们不是当前开发控制不合格的解释。
- 当前完整机械链和直接部署兼容已有记录。先核对最新实现与 fixture 证据，复用已完成工作；不重新建设 selection lock、Provider、schema 或治理框架。

本轮尚未发出新的模型提议，因此这次失败属于控制设计/观测和采集问题，不能归因为模型不会学习。[R1–R4]

## 2. 先修控制的可观测性，不先触发新故障

### 2.1 零 Provider、零故障激活的资格核对

在新槽位被使用前，明确写出一页采集方案：

1. `D_CORE_FIX_01` 使用哪一个**原授权范围内、已有且固定版本的已知故障控制**。优先沿用 payment 控制；只有能说明旧控制无法提供所需证据时，才从已有控制目录中明确选择其他适用的已知控制，并记录变更原因。
2. 在不改变当前 Core/Extension 诊断逻辑的情况下，该控制预期满足哪一条已有支持条款；每个必要谓词来自什么实际来源、查询、覆盖和窗口。
3. 分别说明“故障服务能够被正常诊断”和“学习目标服务有足够完整的负例观测”。获得 payment 的错误证据，不等于 fraud-detection 的所有必需来源已经完整。
4. 预先固定激活方式、窗口、请求量、采样和结束条件。不在观察到终态后延长窗口、调整强度或重复运行直至得到 Known。
5. 说明它是一般已知故障回归控制还是同症状混淆控制。没有相同症状就不宣称具有相同症状区分能力，也不得悄悄取消原协议必须覆盖的混淆要求。
6. 确认后续 N6 可采用同一经过开发确认的采集方案；不能把 N6 当作第一次试验采集器的机会。

若原目录不存在可满足要求的控制或来源能力，返回具体缺失条款，不花掉唯一新增槽位。不能为取得控制标签删除门槛、注入 `first_error_location=true`、把 evaluator 真值转换成观测，或新增生产访问权限。

### 2.2 允许的修复

只修复有可复现证据的采集/序列化/绑定缺陷，并增加聚焦测试。已修的 ID 排序与请求模型校验应在任何槽位预留、故障激活前执行。

必要的新增诊断材料应来自正常授权读路径，只保存在项目私有、受限的证据存储。原始 trace 父子关系只能从确实取得的材料验证；不能从旧摘要逆推出未保留的关系。不得为通过门槛修改当前诊断含义、来源上限、信任边界或既有查询语义。若确需这些变化，先报告具体额外范围，本文件不授予该扩大。

持久化新的采集输入和实际错误材料，避免出现“只保存失败哈希，关键数据随后被清理”的再次信息丢失；但不得公开原始日志、密钥或私有注入真值。

## 3. 追加开发数据契约，而不是把 N3 改成成功

开发采集可以在修复后进行一次新的、明确标识的实验；不允许把它伪装成原实验没有失败。

在新故障激活前，追加一个有父版本的开发数据契约，绑定：旧 plan/结果摘要、新槽位 ID、修复版本、控制与采集方案、新预算授权、适用环境以及未消耗的 N4–N7。

- 原 N1/N3 的 reservation、terminal、incident、诊断、observations、角色和历史失败 verdict 均不可修改。
- 新 `D_CORE_FIX_01` 是独立、已见的 DEVELOPMENT 事件。不得沿用 N3 的 ID、出生记录、时间窗或槽位；这是公开记录的新资格控制，不是隐蔽替换旧分母。
- 原协议“已知开发控制必须为 CORE_KNOWN / EXTENSION_KNOWN”的要求保留。新的协议明确使用 `D_CORE_FIX_01` 承担该角色，N2 仍承担健康控制；旧 N3 不升级为已知对照。
- 原 N3 继续作为“观测不足事件”保留并报告。若可用旧材料用于补充安全检查，规则不得错误匹配为 TRUE；原始 UNKNOWN 保持 UNKNOWN，不能计作完整负例 TRUE NEGATIVE 或特异性成功。
- 报告中分别列出开发控制采集尝试数、有效控制数、失败/观测不足数；不能只展示新成功控制并抹去旧 N3。
- 原 e01–e05 均保持已见，原 Level A 条件仍要求 e04/e05 均 TRUE、原五例至少 4/5，以及完整健康/已知控制不被规则误吸收。不能挑选一两个恰好满足的原事件。
- 在当前没有真实候选选择锁、没有 N4–N7 数据消费的条件下才允许安装本次契约。若最新状态已变化，先核对并停止冲突操作，不强行适用旧起点。

实现应复用现有追加式 split、budget、runner。老协议照旧可审阅和重放，新契约不能重写其失败结论。只增加本次所需的明确槽位和父版本，不再建设通用实验调度平台。

## 4. 一次新开发采集，成功后连续推进

### 4.1 环境准入

遵守原有 owned 资源、Docker 稳定性、固定镜像/上游、健康基线和精确 cleanup。此次允许为有明确用途的新开发控制以及后续既定 N4–N7 创建必要的 owned 部署，并保留每个部署的新身份与直接原始能力比较。

不得自动重启 Docker、修改 Resource Saver/网络、停止外部任务或清理非项目对象。出现新非项目漂移仍停止相关动作，不循环刷新基线。不能根据上一次 clean=true 声称当前一定安全。

### 4.2 新事件资格检查

先完成 typed payload、查询与采样可行性检查，再预留 `D_CORE_FIX_01`，之后执行一次预先确定的采集。正常 Product API/Worker 必须自己得出满足资格的已知诊断。

若新事件仍为 `INSUFFICIENT_EVIDENCE`、失败、覆盖不足或无法恢复健康：保留新失败、按实际规则计入新增额度、精确 cleanup，停止该补采轮。没有第二个隐含重试额度，不运行 N4–N7。

若成功：形成新开发输入清单并冻结其来源，直接返回原 final-learning-closure 的模型开发流程，无需因阶段转换再请求同一授权。

### 4.3 真实模型开发

保持已工作的模型和 Responses 配置；沿用本闭环轮未使用的请求/费用/语义次数，不重开过去已经耗尽的其他轮次。

模型输入必须有逐事件、逐条件 TRUE/FALSE/UNKNOWN，旧候选和拒绝原因，新健康/已知对照及旧 N3 的缺口。不给手写通过规则、正确阈值、注入命令、测试答案或未来 holdout 数据。

Runtime 继续只做机械绑定、真实求值和门槛检查；不删掉模型所选的不成立条件。优先尝试一次真实候选，按原有六次总语义上限做有信息的修订；同一执行条件重复也计数。无新增信息不盲目重试。

Level A 首个达到既定开发门槛的候选出现后立即锁定，不再挑选其他候选。本轮最终上限仍为 `PASS_LEVEL_A / LIMITED`；不因给足了新的开发控制，就自动把 N1 缺口或 Level B 要求视为满足。

## 5. 固定 N4–N7，完成独立验证与复用

在任何 N4–N7 原始数据被查看/消费前，固定新开发契约、候选、控制采集方案、模型/prompt/schema、求值器、部署兼容策略和不变的评分门槛。尤其明确 N6 采用的已知控制采集方案已经在开发侧验证过，不能边看 N6 边修。

- N4：独立目标正例。
- N5：独立健康控制。
- N6：独立已知/混淆控制，须满足原 stratum 的证据与诊断要求。
- N7：仅在 Shadow 通过且隔离测试注册库晋升后，执行的独立新事件复发。

N4–N7 保留原身份、角色、次数和原剩余额度，绝不用于这次开发重试。新协议变更在验证之前追加声明；若某槽已有任何曝光，就不能将其继续称为盲测。

继续原 Shadow 门槛、派生安全控制、测试晋升、正常 API/Worker 依赖采集与 matcher、零 Provider 调用增量验证，以及撤销后的显式回放。单元测试、预插 ACTIVE、故障开关复位和脚本直接调用 matcher 都不能代替真实闭环。

独立验证失败就保留失败；禁止根据结果改规则、改采集强度、换控制或追加样本追求 PASS。当前小样本结果只证明有界本地闭环，不宣称生产覆盖率、普遍特异性或因果发现。

## 6. 交付与避免重复收尾

继续 PR #104；不自动 merge/tag/release/deploy。Product 恢复保持 preview-only，实验复位与清理不是 Agent 自主恢复。

只追加一个小的本次数据契约和结果章节，复用现有 verifier。先聚焦回归与一次机械贯通；有稳定交付 HEAD 后做必要全量检查，不在每个正常采集步骤重复跑全量。

最终优先给出：

| 层级 | 必答项 |
|---|---|
| 采集修复 | 修了什么，为什么预计得到真实证据；未能确定的根因是什么 |
| 开发数据 | N1/N2/N3 原结果、新 D_CORE_FIX_01 结果、尝试与有效分母 |
| 模型效果 | 实际新调用、选择条件、开发 TRUE/FALSE/UNKNOWN、是否通过 |
| 独立闭环 | N4–N7 实际是否使用、Shadow、晋升、正常入口零调用复用、撤销 |
| 预算/权限 | 累计上限13和本轮8是否已显式激活、已用数、原 Provider 余额、cleanup |

没有新有效数据就报告采集阻塞；有数据但模型规则不成立就报告开发失败；有独立验证失败就报告独立失败。不能统一用“又增加单测，工程已完成”覆盖这些区别。
