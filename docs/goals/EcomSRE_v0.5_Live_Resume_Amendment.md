## 3. 先处理候选输入与观测依赖，再扩大真实运行

本次 schema-valid 候选包含 CPU mean 表达式，但没有通过各成员事件的可部署观测依赖检查。[R2][R3]

该检查要求存在已绑定的补查观测、正确目标/相对窗口及支持引用；不能删除这个检查来让候选入库。[R5]

先用现有记录确认并区别：

1. 数据根本没有采集；
2. 数据存在，但目标、相对窗口、字段/采样语义或引用不匹配；
3. 可部署读取模板存在，但模型视图未明确表达可选依赖；
4. 提议 schema 的单位/算子/窗口等约束不清，产生格式或表达式错误。

### 3.1 需要的最小处理

- 查看实际知识请求投影和拒绝原因，不只查看最终 `KNOWLEDGE_CANDIDATE_REJECTED`。
- 将“已经取得且可验证”“合法可查但尚未采集”“当前不支持”明确区分。
- 必要时把现有、可部署的读取依赖以有限目录投影给模型：来源、合法目标、字段/单位、相对窗口、采样要求及可解析引用。复用当前目录和绑定，不建设新平台。
- LLM 可以选择依赖并提出规则，但不能声称未读取的数据已经支持规则。缺数据应先调查或报告具体缺口。
- 对尚未收集齐的学习输入，由独立开发协调流程安排调查；实际调查路径仍由 LLM 在多个合法候选中决策。预采集/固定采集部分如实标注，不能计作模型自主选读。
- 不向模型提供手写成功规则、正确阈值、故障注入真值或 holdout 标签；不把 schema 示例变成答案。
- 依赖不匹配时保留拒绝；若确认实现缺陷，先建立具体回归，再作局部修复。

当前 `discovery_view()` 主要提供 session、谓词和资源特征目录；是否还需要更明确的依赖目录，应核对真实模型输入后决定，不能仅凭拒绝就认定某个模块一定有 bug。[R6]

### 3.2 验证输入路径，而不是只添加类型

最少核对一条完整路径：

```text
合法资源读取 → 已绑定真实观测 → 学习视图 → 模型依赖选择
→ 候选检查 → 开发求值 → 新事件同语义确定性读取 → 规则求值
```

同时保留缺失、错误窗口、错误目标的拒绝/UNKNOWN 分支。

修复只需聚焦回归；在稳定交付 HEAD 形成之前，不为每个小步骤反复跑全量测试。

## 4. 恢复原 Live 主线：先证明一个可行事件，再按原拆分推进

### 4.1 启动前只做必要检查

核对现存容器/网络/卷、资源所有权、固定镜像与上游、端口、可用本地资源、原账本路径和工作区改动。不能通过停止未知服务或全局清理腾出资源。

选择能提供实际 Level B 观测的最小原有场景。不要求一定是 Kafka；不能凭空假定已有 partition lag/consumer throughput。明确目标模式为何未被当前有效知识充分解释。

使用新建隔离测试环境和注册库；不能为制造未知故障删除用户已有 ACTIVE 规则、关闭 Core 匹配或降低已有阈值。

在批量运行前把实际可执行的场景、控制方法、来源能力、目标/混淆控制和拆分登记到现有 manifest。开始的是新 campaign，不是重跑历史冻结研究。

### 4.2 首个独立 Discovery episode

健康确认 → 在已授权 owned 资源上触发受限条件 → 实际遥测 → Product 诊断与 LLM 调查 → 状态恢复/健康确认；保留完整边界。

首个 episode 可以计入原计划的 discovery，而不是另开一份预算。不要把一段持续故障切成多个窗口增加独立分母。

原 smoke 的 3-call 上限是协议检查配置，不是所有正式调查的强制上限。正式调查可使用原 Goal 已允许的每 session 最多 10 次 Provider 请求、8 次证据读取，仍遵守无进展停止和总账本。不得设置无限调用或在失败后无限续 session。

观察实际是否出现：模型提出可检验解释、选择区分性读取、消化结果、修订候选或调查路径。单纯 READ→READ 和文字变动不能冒充诊断能力证明。

若没有可用数值来源、读取语义不成立或事件实际上已被 Core 充分解释，准确定位再继续；不硬制造“未知”和成功。

### 4.3 学习与独立验证

复用原 Goal 的开发/盲测分离和最小案例要求，不另建 skill 对照。

- 完整验收仍至少需 3 个独立本地 discovery episode，以及冻结后 2 个独立本地验证/复发 episode；开发与控制案例按原计划管理，全部 live 总数不超过 12。
- 学习只接收 discovery/development 的实际材料和可部署依赖；模型候选保留 origin、请求绑定、修订与拒绝原因。
- 维持原有候选/开发修订上限，不通过连续重试挑选恰好通过的输出。不能把临时故障模式命名当作因果发现。
- 开发检查通过后，冻结模型/配置、prompt/schema、候选、依赖语义、求值器、案例拆分和评估协议，再运行独立测试。
- 同症状混淆、健康、Core、来源失败/覆盖不足及目标歧义控制按原 Goal 披露；不可将派生控制当作独立 live episode。
- 学习/修订不得使用 holdout；独立测试失败不能靠修改阈值、换候选 ID、重命名 episode 或追加挑选样本改成 PASS。
- 通过原有准入后，仅由独立治理/harness 晋升到本次新建测试注册库，记录条件式预授权来源；模型无晋升权限。
- 再用此前未暴露的独立新事件走正常 Product 入口，验证依赖读取和 `EXTENSION_KNOWN`，并记录该新事件 LLM calls = 0。

没有可验证的模型规则就拒绝。完整成功不是本补充保证发生的结果。

## 5. 预算与停止条件

沿用原总上限：200 次 Provider 请求、USD 20 累计成本/承诺上界、12 个本地 live episode。历史 24 次请求和 USD 0.232264 承诺不清零；新工作均计入原账本。

Provider 排障 P1/P2 的 6 请求/USD 1 子上限只适用于已完成的入口定位，不作为本地学习 campaign 的新上限，也不产生额外额度。新的正常调查、知识提议、修复和预览使用原剩余总预算。

普通阶段结束不再次申请同一授权；只有实际超范围资源/权限、预算触顶、观测能力不支持、无法安全清理或其他原 Goal 的真实阻塞才停。不得通过扩大授权或放松验收消除阻塞。

先推进一个有实际意义的 live episode，确认遥测/调查可行，再按计划继续；不要以“可以启动 Docker”代替能力验收，也不要再在已解决的最小生成上消耗预算。
