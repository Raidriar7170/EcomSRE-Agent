01 / PROBLEM

项目一句话与问题定义

面向微服务故障定位的可验证 SRE Agent：不是让模型自由操作环境，而是让每个诊断都能回答“用了什么证据、覆盖是否完整、为什么允许得出这个结论”。

面向需要分析多服务告警的开发者和 SRE。指标、日志、调用链和运行状态是异构且不完整的：服务别名可能不一致，进程健康不代表没有积压，没查到日志也不等于没有故障。

LLM 善于组织解释，但可能编造目标、工具或行动。当前系统把候选、读取边界、谓词、引用、诊断准入和权限放在确定性 Runtime。模型只作为可选的非权威命名与解释层。

项目叙事只有三个阶段：证据驱动的可靠诊断 → 可部署的只读 Product MVP → 开放世界发现与人引导知识演化。历史试验与失败单独保留，不要求读者先理解所有微版本。

02 / ARCHITECTURE

最新架构图

读图顺序是环境与证据、固定诊断顺序、环境内知识循环。多个来源提供观测，不是多个模型投票；知识晋升改变扩展库，不改变动作权限。

移动端可横向查看完整图；打印使用自适应 SVG。前三种准入结果直接输出诊断；冲突或证据不足保留不确定性。详细架构 · Mermaid 源文件

03 / EVIDENCE

证据驱动诊断

环境登记先归一服务身份，验证连接器并建立能力矩阵。多窗口 Baseline 显式激活后，事件冻结它与服务映射的绑定。每次读取保留服务、来源、窗口、覆盖度和状态，规范化观测进入不可变 Evidence Store，Salient Memory 整理支持谓词的事实。

PRESENT 是已有支持证据；ABSENT_WITH_COMPLETE_COVERAGE 才是可用反证；UNKNOWN 与 SOURCE_FAILED 都不能被当成“没有异常”。哈希保证内容绑定，不保证传感器天然正确。

判断固定为 CORE_KNOWN → EXTENSION_KNOWN → NO_INCIDENT → OPEN_WORLD。如果多条规则冲突或证据不够，保留 CONFLICTING_EVIDENCE / INSUFFICIENT_EVIDENCE，不能为输出一个答案而隐藏缺口。

健康系统同样需要证明：孤立短窗口内存增长不单独形成强残差，必须有同服务独立佐证。这里区分冻结 Core 规则与 Product 残差策略，不把它们混成“调低阈值让测试通过”。

04 / PRODUCT

只读 Product MVP

FastAPI 接收事件、验证请求并提供查询接口；Worker 领取 SQLite 租约任务，执行连接器验证、Baseline 和诊断。SQLite WAL 保存产品状态，CAS 内容寻址存储保存证据对象。提交时 fencing 防止过期 Worker 发布结果。

Product 可以写自己的数据库、证据和治理记录，但不能写被诊断系统。Compose 不挂 Docker socket，API 仅发布到 loopback。真实实验中的资源创建、故障注入与清理属于独立、显式授权的本地实验控制器。

可运行入口是Docker-free 确定性演示：进程内 TestClient、合成遥测、模拟人工记录、扩展复发与应用重启验证；没有外部模型调用，不是 Kafka 实验的复跑。

API 的 /v1、Python 的 V1 类型与数据库 schema 是兼容性标识，不因公开 v0.3 标签改名。后台任务与知识治理接口也不能仅凭 URL 中的 jobs 一词混为一谈。

05 / KNOWLEDGE

开放世界知识演化

未知强异常不是直接加入核心类型库。Runtime 生成指纹，在相同环境用异常、来源、领域、根服务、拓扑和状态的加权相似度聚类；这是确定性特征比较，不是文本 embedding 或一次模型猜测。

  1. 发现未解释异常OPEN_WORLD → Incident Fingerprint
  2. 积累多事件故障族不同窗口，检查根一致性和证据
  3. 人工接受为新类型Human ACCEPT_AS_NEW
  4. Runtime 挖掘规则正负例矩阵，长度 1–3，beam width 20
  5. Shadow + 人工晋升先验证误报、冲突和来源失败
  6. 环境扩展识别复发ACTIVE Registry → EXTENSION_KNOWN

候选规则以召回、误报、重叠和复杂度评分；最终 Shadow 比挖掘候选更严格。只有完整覆盖的缺席可作负证据，未知和来源失败不能让弱规则“侥幸通过”。可选 LLM 仅建议标签与解释，不选择晋升关键谓词、不批准 Promotion。

数据不足就继续积累或返回需要更多负例；晋升不是一次模型自我审批。完整契约与阈值见知识演化说明。

06 / END TO END

健康环境与未知故障两条完整流程

健康路径：先证明覆盖，再说没有事件

登记环境并验证来源 → 激活多窗口 Baseline → 读取 checkout 的 Metrics / Resources / Logs / Traces / Runtime → 核查覆盖与健康证据 → 返回 NO_INCIDENT → 保存诊断和证据。实测 30/30 事务成功，No-Fault scorer FULLY_SUPPORTED，能力限制为 0；不代表所有服务长期健康。

未知路径：从第一次观察到下一次识别

N0-A / N0-B 健康控制各 30/30；C1 已知配置故障定位 payment，并确认队列阴性。随后 P1 / P2 / P3 三个窗口都进入 OPEN_WORLD，领域 CONCURRENCY、根服务 fraud-detection，组成一个三成员故障族。

Runtime 从三个正例、三个实测负例选出 core:RUNTIME_HEALTHY AND ga:METRIC_QUEUE_LAG_OUTLIER。Shadow 通过后仅晋升一个 kafka-queue-backlog 扩展。晋升后新采集 H1 返回 EXTENSION_KNOWN，根服务与故障族多数根一致，不再生成临时报告或新族。

H1 验证的是“新规则真正进入诊断路径”，不是跨环境泛化。C1 的无关 Logs / Traces 缺口仍然保留，不能说整个实验每个来源都完整。

08 / TRADE-OFFS

设计取舍

不用模型自由路由换取“智能感”

复杂 Multi-Agent 的冻结比较没有支持预注册优势；真实故障取证的小样本里模型自由路由弱于确定性方案。因此当前优先把证据选择、覆盖和准入做成可检查契约。这不是 Multi-Agent 普遍无效的证明，见历史索引与原始结果。

未知不等于可注册，格式有效不等于语义正确

早期注册辅助研究中，结构全部合法并没有换来正确机制重建。当前让 Runtime 从多事件正负例挖规则，模型仅负责命名解释；代价是知识演化更慢、需要足够数据与人工门控，但错误不会直接扩展执行能力。

持久化原型与生产平台分开

SQLite / 单 Worker 简化本地部署与审计，但没有证明高可用或大规模并发。检查点让失败可恢复，不能抹去失败，也不能自动证明原始错误根因已定位。

贡献边界

最强项目贡献是证据契约、可持久化只读 Product、环境内知识闭环。个人讲述需区分实际承担的设计、实现、评估和协调；不能因为仓库属于自己就声称全部独立手写。上游 OTel Demo 是被观测环境，FastAPI 等框架能力不算个人自研。

没有通用延迟、成本或生产 SLO 数据；不要用测试耗时当线上指标。本次知识闭环不依赖模型调用，不应用训练或微调收益解释它。

10 / INTERVIEW

高频问答

为什么不是 Multi-Agent？

先证明复杂度收益。历史冻结比较收益不稳定，当前将取证和准入收敛为确定性 Runtime；保留模型解释能力，不把代理数量当质量指标。

LLM 到底做什么？

可选标签和解释。它不选晋升关键谓词、不定诊断根、不审批、不执行；本次 live Provider = 0。不是通过微调或向量 RAG 完成该知识闭环。

如何保证证据有效？

服务、时间窗口、覆盖度、引用和内容摘要逐层绑定；缺失与反证分开。完整性不是传感器正确性，连接器与算法仍需测试。

如何防健康误报？

实际流量与健康证据共同验证；孤立短时资源波动需要佐证；Shadow 必须包含健康控制且不能误报。有限窗口不等于长期零误报。

怎么发现未注册故障？

强异常没有被 Core 或环境扩展解释时形成 Open-World 报告，再按环境内特征聚类。不是凭空生成一个已验证机制。

怎样挖规则并晋升？

人工接受故障族，Runtime 建矩阵、搜索规则、运行 Shadow，最后人工晋升；实测规则要求运行健康与队列异常同时成立。

为什么 H1 有意义？

晋升后新采集窗口命中持久化扩展，并保持根服务一致，无新族或临时报告。证明实际匹配链路生效，不证明跨环境泛化。

距离生产还差什么？

独立机制与环境、其他扩展干扰、长期负载/健康窗口、多租户、HA、安全和恢复验证。当前是只读原型，不承诺自主修复。

11 / BOUNDARIES

限制与下一步

已验证一个有界本地 OTel 多服务环境、一个学到的 Kafka 队列积压机制。单租户 SQLite 没有长期规模、HA 或 Kubernetes 生产控制面验证；本地阈值不保证跨环境有效，部分完整 live 遥测、DB 与镜像锁未提交。

治理说明：本次 ACCEPT_AS_NEW 与 Promotion 使用用户明确的事先授权，不是运行中重新逐条人工检查。OTHER_EXTENSION 分层不可用，不代表真实其他扩展重叠实验已经通过。两项边界都保留在证据中。

下一步先补独立环境和机制、长期健康负对照、其他扩展冲突、聚类拆合质量与部署恢复，再讨论更强产品化；这些是方向，不是已经执行或自动授权的实验。
